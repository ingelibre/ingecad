# Languages in IngeCAD — the rule, and the plan

This document exists because a contributor asked a question
([#4](https://github.com/ingelibre/ingecad/issues/4)) whose answer only lived
in the maintainer's head. It is in English because it is written for
contributors.

## The rule, in one sentence

**Everything you read is translatable; everything you type is English.**

IngeCAD's whole reason to exist is that an AutoCAD user types what their
fingers already know — `L`, `TR`, `Z`, `E` — and it works. So the command line
is English in every language of the interface, and it always will be. Menus,
dialogs, panels and prompt *text* are translated; command names and the option
keys inside prompts are not.

### What that means for a prompt with options

A prompt like

```
Specify rotation angle or [Reference]:
```

is parsed against the English key `R`. So the translation must keep that key
visible. The convention is: **translate the word, keep the English letter in
parentheses.**

```json
"Specify rotation angle or [Reference]:":
    "Especifique el ángulo de rotación o [Referencia(R)]:"
```

A translation that drops the letter — `[Referencia]` — produces an interface
that offers the user a word and then rejects it. That is the bug reported in
#4, and it is the one thing a language file must never do.

Multi-letter keys work the same way: AutoCAD's `CEnter` is `CE`, so the Spanish
is `Centro(CE)`.

## Adding your language

Today a language is one flat `{english: translation}` map in `i18n/<code>.json`
(`i18n/en.json` is the identity map and stays empty). After phase I2 below it
becomes a directory; the rule above does not change either way.

1. Copy `i18n/es.json` as a model — it shows the bracket convention in use.
2. Translate what you can. **Partial is fine**: a missing key falls back to the
   English source string, so an incomplete file degrades to readable English,
   never to a broken key or a crash. No release is ever blocked on a
   translation.
3. Keep every English letter inside `[...]`. A test enforces this.
4. You own your file. Nobody else will silently rewrite it.

## Why not translate the commands too?

Localized AutoCAD *does* translate command names — a Spanish install really
does take `LINEA` and `BORRA`. But it also accepts every command's English name
prefixed with an underscore (`_LINE`), which is why a LISP routine written in
Spain runs on an English install. Autodesk translated the surface and kept
English as the lingua franca underneath.

IngeCAD will get there (phase I4), with the same guarantee: **the English name
never stops working, in any language.** It is last on the list because it is
the part that must never break, and because no user has asked for it yet — the
target market types English today.

# The plan

The design goal is that **a language is a package, not a patch**: adding one
should be dropping a folder, with no Python change. Today it is not — the
language menu carries a hard-coded list, which is why the Czech PR had to touch
`views/main_window.py`.

Target layout:

```
i18n/
  en/  meta.json                          <- source language, empty catalog
  es/  meta.json  ui.json  commands.json
  cs/  meta.json  ui.json                 <- commands.json is optional
```

with `meta.json` carrying what is hard-coded today:

```json
{ "code": "es", "name": "Español", "maintainer": "…", "status": "complete" }
```

and `core/i18n.py` (74 lines) growing into a package **without changing its
public API** — `tr()` stays exactly as it is, so no caller is touched:

```
core/i18n/
  __init__.py   tr(), set_language(), available_languages()   <- unchanged
  packs.py      discovers and loads language folders, reads the legacy layout
  keywords.py   the prompt-option resolver
  commands.py   localized command names + the _ prefix
```

## Phase I0 — write the rule down and enforce it  (~1 session)

No architecture change. This is what unblocks contributors.

Done on 2026-08-22, except the merge, which waits on the contributor.

- Fixed the **17 Spanish translations** that drop the English key: LAYOUT, all
  five OFFSET prompts, both AREA modes, MVIEW, BREAK, CHAMFER and its trim
  mode, PEDIT, ARRAY and UNITS. 70 of the 87 bracketed strings already
  followed the convention.
- Added `tests/test_i18n_prompt_keys.py`, which walks every language file.
  Reverting `es.json` turns it red with 29 named options; with the fix it is
  green, and 715 tests pass.
- `CONTRIBUTING.md` now carries the rule (the file did not exist before).
- The Czech translation merges once it follows the convention.

**Two things the audit turned up that the first count got wrong.** The
convention has three accepted spellings, not one: `Suprimir(D)`, or the
capitals of the word carrying the key as AutoCAD writes them (`CEntro` = CE),
or the keyword left untranslated (`3P`, `Ttr`). Counting only the parenthesis
form called 28 strings broken when 17 were. And options must be compared **by
position**: a loose any-to-any check accepted `Definir` (which is Set) as the
translation of `Delete`, because both carry a capital D.

**And one defect on the English side**, which is the point of making the rule
checkable: OFFSET's prompt reads `[Exit/Undo]`, so its key is `E`, but the
tool only accepted `X`. It now takes both (`tools/edit.py`).

## Phase I1 — Spanish coverage  (~1 session)

Done on 2026-08-22. `es.json` went from 974 keys to 1216, and the coverage
report reads **es: 1110/1110 (100%)**.

- The **274 `tr()` strings** with no Spanish entry are translated. `es.json`
  was written for v0.2; v0.3/v0.4 (tables, images, QuickCalc, QSELECT, GROUP,
  draw order, the options dialog) landed without it.
- `tests/test_i18n_coverage.py` **fails only for the maintained language**
  (`es`). Community packs are reported, never enforced: an incomplete file
  falls back to readable English and must not block a release.
- It also checks, **for every language**, that a translation keeps its
  `{placeholders}` — `tr()` formats the translation, so a dropped `{count}`
  swallows data and a misspelt one raises in front of the user.
- Verified the way this project asks for: reverting `es.json` turns the tests
  red naming all 274; the real window built in Spanish walks 132 menu labels
  with none left in English; 720 tests pass.

**Two traps this phase walked into, both worth remembering.**

*The scanner has to be checked before its output is.* The first pass reported
138 "dead" keys in `es.json`. Most were not dead: **106 strings never appear
inside a `tr(...)` call at all**, because they live in a data table and are
translated later through a variable — `Mode("END", 1, "Endpoint")` in
`core/osnap.py` reaches `tr(mode.label)`. Deleting them would have silently
un-translated the osnap markers. The dead-key test now asks whether the key
matches *any* string literal in the sources, not just a `tr()` argument. 32
were genuinely dead — old wordings of prompts reworded during the
draw-command audit — and were removed.

*And a check that walks nothing passes.* The first Spanish smoke test reported
"0 menu labels, 0 untranslated" and looked green; the label walk was simply
finding no menus (`main_window` keeps its own `_menu_bar`, so `menuBar()` was
empty). A count of zero is never a pass — the fixed walk sees 132.

## Phase I2 — the language folder  (~1 session)

Done on 2026-08-22.

- `core/i18n.py` is now the package `core/i18n/`, with `packs.py` doing
  discovery. The public API did not change — `tr()`, `set_language()` and
  `available_languages()` behave as before, so no caller was touched — and it
  gained `language_packs()` and `language_name()`.
- **Both hard-coded language lists are gone**: the Tools ▸ Language menu
  (`views/main_window.py`) and the Options combo (`views/options_dialog.py`)
  are built from the installed packs.
- `en` and `es` migrated to folders. **The old flat `i18n/<code>.json` still
  loads**, so the Czech translation in flight keeps working unconverted; a
  folder wins over a leftover flat file of the same code.
- `maintained` moved into `meta.json`, so the coverage test of I1 no longer
  hard-codes which languages it enforces. Adding a language now touches no
  Python **and no test**.
- `main.py --check` reports the discovered languages and fails when a bundle
  ships none — a packaging loss that otherwise looks like a working
  English-only app.

**DoD, verified end to end:** dropping `i18n/qu/{meta,ui}.json` into the tree
and building the real window puts *Runa Simi* in the Language menu, with no
code change; removing it takes it away. 727 tests pass.

## Phase I3 — the keyword resolver  (~2 sessions)

Done on 2026-08-22.

`core/i18n/keywords.py` takes a prompt's English source and its rendering in
the active language and returns everything that answers it:

| typed | where it comes from |
|---|---|
| `D` | the English key — **always**, in any language |
| `DELETE` | the English word — **always** |
| `SUPRIMIR`, `suprimir` | the translated word, accents optional |
| `_D`, `_DELETE` | the explicit global form, as AutoCAD writes it |

Everything resolves back to the **English key**, so call sites keep comparing
against `"D"` and never learn other languages exist.

**The migration turned out smaller and safer than planned.** The plan said to
rewrite the 143 hand-rolled comparisons. What actually shipped normalizes the
token at the door instead — 34 `on_option` methods now open with

```python
t = self.option(text) or text.upper()
```

so every existing branch works unchanged: `self.option()` returns the English
key, which is already the first element of every one of those tuples, and the
fallback preserves today's behaviour exactly when the token is not an option
at all (a number, a coordinate, an entity type). Same guarantee, a fraction of
the risk. The comparisons stay, but nothing parses a keyword any more.

**What did have to change everywhere is where prompts come from.** A prompt
whose `{placeholders}` are filled in cannot be mapped back to the catalog
entry that lists its options, so the source string has to survive. All 286
prompts in `tools/` now go through `Tool.prompt(source, **kw)`, which
translates *and* remembers. That is not tidiness: it is what makes a stale
option set impossible. A prompt with no options clears them, so a `D` typed as
a distance can never be eaten by an earlier prompt's Delete — there is a test
for exactly that.

The flows that are not tools — LAYOUT, LAYER, UNITS, ZOOM — pass their source
explicitly, since their prompt text is already a module constant or right
there in the call.

**Two things the work turned up:**

*A digit is part of a key.* `_capital_key("2P")` returned `"P"`, because `2`
is not an upper-case letter — so CIRCLE's first prompt had `2P` and `3P`
resolving to the same key. The existing suite caught it on the first run.

*And the mechanical rewriter needed to know two indentation styles.* Pulling
`self.ctx.prompt(tr(` back to `self.prompt(` moves continuation lines that are
aligned to the old opening paren, and must leave hanging indents alone.
Getting that wrong produced valid-but-ugly code the first time and, when
stripping `tr(` from the helpers that *return* prompts, invalid code — those
parentheses were what allowed the implicit string concatenation, so there the
rewrite keeps them: `tr(` becomes `(`. Every rewrite re-parsed its own output
before writing, which is what turned that into a caught error rather than a
broken tree.

**DoD, verified:** in Spanish, `Suprimir`, `D` and `_D` all delete a layout,
driven through the real `layout_command` flow; `Distancia`/`D`/`_D` all open
CHAMFER's distance prompt; LAYER takes `Imprimir` and `No imprimir`. A test
reads each option off the prompt the tool actually printed and types it back,
so anything offered is answerable. Sabotaging the resolver turns 11 of those
red. 754 tests pass, and the audit finds no keyword parsed by hand outside the
resolver.

## Phase I4 — localized command names  (~1–2 sessions)

Done on 2026-08-22.

```json
i18n/es/commands.json
{ "LINE":  {"name": "LINEA"},
  "ERASE": {"name": "BORRA", "aliases": []} }
```

`Dispatcher.resolve_name` (`core/actions.py`) now resolves in this order, and
**English comes first at every step**:

1. a leading `_` is AutoCAD's global form — English only, so a script or a
   macro runs whatever the interface language;
2. the English alias table, then an exact English command name;
3. the active language's own names;
4. prefix completion, English before localized.

Spanish ships with **58 names**: LINEA, CIRCULO, BORRA, DESPLAZA, RECORTA,
ACOLINEAL and the rest of the daily set. Autocompletion offers them too.

**The invariant, and how it is held.** A language pack may only *add* names.
`core/i18n/commands.py` refuses a pack that names a command this build does
not have (a typo that would simply never fire), that claims a token English
already answers to, or that gives one token to two commands. The test walks
**the whole `DEFAULT_ALIASES` table under every installed language**, checking
the alias, the command name, and both behind `_`. Adding `"aliases": ["L"]` to
a Spanish entry turns it red with *'L' would shadow the English alias 'L' =
'LINE'* — verified by doing it.

That is also why the shipped pack declares no aliases: the English
one-letter aliases *are* the muscle memory the product is built on, so nearly
every short alias a language would want is already taken. Names are additive;
aliases mostly are not.

**Verified end to end**, typing into the real command line of a real window
with Spanish active: `LINEA`, `L`, `_LINE` all start LINE; `BORRA` starts
ERASE; `CAPA` starts LAYER. In English, `LINEA` resolves to nothing — a
Spanish name is a Spanish name, not a second English one, which is how
AutoCAD behaves too. 767 tests pass.

⚠️ **The Spanish names are my best reading of AutoCAD's Spanish, not a
verified list.** They are additive, so a wrong one costs nothing but a name
nobody types; the file says so and invites corrections, and changing one is
changing one string.

## Order and honesty

Each phase ships on its own. Stopping after I1 already leaves everything
coherent. **I0 is the one worth doing now**, because until the rule is enforced
every new translation can reintroduce the #4 bug. I3 and I4 are worth doing
when a user asks for them — today the target market types English.

Rough cost: I0 + I1 ≈ 1 session, I2 ≈ 1, I3 ≈ 2, I4 ≈ 1–2.
