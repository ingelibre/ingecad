# Languages in IngeCAD — the rule, and the plan

This document exists because a contributor asked a question
([#4](https://github.com/ingelibre/ingecad/issues/4)) whose answer only lived
in the maintainer's head. It is in English because it is written for
contributors.

## The rule, in one sentence

**Everything you read is translatable; everything you type is English.**

IngeCAD's whole reason to exist is that an AutoCAD user types what their
fingers already know — `L`, `TR`, `Z`, `E` — and it works. So the command line
is English in every language of the interface, and it always will be. Menus,
dialogs, panels and prompt *text* are translated; command names and the option
keys inside prompts are not.

### What that means for a prompt with options

A prompt like

```
Specify rotation angle or [Reference]:
```

is parsed against the English key `R`. So the translation must keep that key
visible. The convention is: **translate the word, keep the English letter in
parentheses.**

```json
"Specify rotation angle or [Reference]:":
    "Especifique el ángulo de rotación o [Referencia(R)]:"
```

A translation that drops the letter — `[Referencia]` — produces an interface
that offers the user a word and then rejects it. That is the bug reported in
#4, and it is the one thing a language file must never do.

Multi-letter keys work the same way: AutoCAD's `CEnter` is `CE`, so the Spanish
is `Centro(CE)`.

## Adding your language

Today a language is one flat `{english: translation}` map in `i18n/<code>.json`
(`i18n/en.json` is the identity map and stays empty). After phase I2 below it
becomes a directory; the rule above does not change either way.

1. Copy `i18n/es.json` as a model — it shows the bracket convention in use.
2. Translate what you can. **Partial is fine**: a missing key falls back to the
   English source string, so an incomplete file degrades to readable English,
   never to a broken key or a crash. No release is ever blocked on a
   translation.
3. Keep every English letter inside `[...]`. A test enforces this.
4. You own your file. Nobody else will silently rewrite it.

## Why not translate the commands too?

Localized AutoCAD *does* translate command names — a Spanish install really
does take `LINEA` and `BORRA`. But it also accepts every command's English name
prefixed with an underscore (`_LINE`), which is why a LISP routine written in
Spain runs on an English install. Autodesk translated the surface and kept
English as the lingua franca underneath.

IngeCAD will get there (phase I4), with the same guarantee: **the English name
never stops working, in any language.** It is last on the list because it is
the part that must never break, and because no user has asked for it yet — the
target market types English today.

# The plan

The design goal is that **a language is a package, not a patch**: adding one
should be dropping a folder, with no Python change. Today it is not — the
language menu carries a hard-coded list, which is why the Czech PR had to touch
`views/main_window.py`.

Target layout:

```
i18n/
  en/  meta.json                          <- source language, empty catalog
  es/  meta.json  ui.json  commands.json
  cs/  meta.json  ui.json                 <- commands.json is optional
```

with `meta.json` carrying what is hard-coded today:

```json
{ "code": "es", "name": "Español", "maintainer": "…", "status": "complete" }
```

and `core/i18n.py` (74 lines) growing into a package **without changing its
public API** — `tr()` stays exactly as it is, so no caller is touched:

```
core/i18n/
  __init__.py   tr(), set_language(), available_languages()   <- unchanged
  packs.py      discovers and loads language folders, reads the legacy layout
  keywords.py   the prompt-option resolver
  commands.py   localized command names + the _ prefix
```

## Phase I0 — write the rule down and enforce it  (~1 session)

No architecture change. This is what unblocks contributors.

- Fix the **28 Spanish translations** that drop the English key (LAYOUT, all of
  OFFSET, AREA, ARRAY, BREAK, CHAMFER, …). 59 of the 87 bracketed strings
  already follow the convention.
- Add `test_translated_prompts_keep_english_keys`: for every key containing
  `[...]`, the translation must carry every English initial.
- Add the *Adding your language* rule above to `CONTRIBUTING.md`.
- Merge the Czech translation once it follows the convention.

**DoD:** reverting any one of the 28 turns the test red; no language file can
lose a prompt key without CI saying so.

## Phase I1 — Spanish coverage  (~1 session)

- The **274 `tr()` strings** with no Spanish entry. `es.json` was written for
  v0.2; v0.3/v0.4 (tables, images, QuickCalc, QSELECT, GROUP, draw order, the
  options dialog) landed without it.
- A coverage test that reports per language and **fails only for `es`** — the
  maintained one. Community packs report, never block.

**DoD:** zero missing in Spanish; the report prints the other languages'
percentage; an incomplete pack still loads and still falls back to English.

## Phase I2 — the language folder  (~1 session)

- `core/i18n/` package; `packs.py` reads `i18n/<lang>/` and keeps reading the
  old `i18n/<lang>.json` during migration.
- **The Tools ▸ Language menu is built from the `meta.json` files**, which
  removes the hard-coded list at `views/main_window.py:796`.
- Migrate `en`, `es`, `cs`.

**DoD:** adding a language is a folder and zero lines of Python; a test starts
the window under every discovered language.

## Phase I3 — the keyword resolver  (~2 sessions)

The heart of it. `core/i18n/keywords.py` takes the **source** string and its
**translation** and returns everything that is accepted:

| typed | where it comes from |
|---|---|
| `D` | English letter — **always**, in any language |
| `DELETE` | English word — **always** |
| `SUPRIMIR` | translated word, parsed out of `Suprimir(D)` |
| `_D`, `_DELETE` | explicit global form, as in AutoCAD |

So localized keywords become a property of the translation file, not of the
code, and no language needs a hand-written table.

Then migrate the ~60 prompt sites in batches (`tools/draw` → `tools/edit` →
`core/layers` + `core/layouts` → `tools/dimension` → `tools/inquiry`),
replacing the 143 hand-rolled `if key in ("D", "DELETE")` comparisons.

**DoD:** with Spanish active, `SUPRIMIR`, `D` and `_D` all do the same thing in
LAYOUT; a table-driven test walks every prompt in every installed language; no
hand-rolled option parsing is left.

## Phase I4 — localized command names  (~1–2 sessions)

```json
{ "LINE":  { "name": "LINEA", "aliases": ["L"] },
  "ERASE": { "name": "BORRA", "aliases": ["B"] } }
```

`Dispatcher.resolve_name` (`core/actions.py:98`) gains one step, in this order:
**`_` forces English** → localized alias/name → English alias/name → prefix
completion over the union of both. The user's PGP file may be localized too.

**DoD, and this is the sacred invariant:** with **any** language active, the
entire English alias table still works — `L`, `LINE` and `_LINE` all draw with
Spanish selected, exactly as today. A test walks all of `DEFAULT_ALIASES`
against every installed language. And the loader **rejects a pack with
collisions** (a language claiming `B` for `BORRA` collides with `B` = BLOCK):
CI catches it, not the user.

---

## Order and honesty

Each phase ships on its own. Stopping after I1 already leaves everything
coherent. **I0 is the one worth doing now**, because until the rule is enforced
every new translation can reintroduce the #4 bug. I3 and I4 are worth doing
when a user asks for them — today the target market types English.

Rough cost: I0 + I1 ≈ 1 session, I2 ≈ 1, I3 ≈ 2, I4 ≈ 1–2.
